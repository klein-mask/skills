# 手順書のフォーマット

```markdown
# <id>: <何を実装するか1行>

ゴール: <完了条件。全ステップ完了時に通っているべきテスト・動作>

## 目次

- Step 1: <一行要約>
- Step 2: <一行要約>

## 既存の不具合

<変更箇所で見つかった既存バグ。無ければこのセクションごと省く>

- <どこで何が壊れているか> → <今回の実装への影響（先に直す / 一緒に直す / 触らず別チケット）>

## Step 1: <このステップで何をするか>

対象: `path/to/file.ts`（新規 or 修正）

なぜ: <この設計・この場所である理由を1〜2行>

<コードブロック>

確認: <このステップ完了時に人間が実行するコマンドと期待結果（red / green）>

## Step 2: ...

## 最終確認

<全テスト・型チェック等、人間がローカルで実行するコマンド>
```

## 書き方の規則

- 目次は写経を始める前に全体像を掴むためのもの。ステップ見出しを1行ずつ並べるだけに収める
- コードを書くステップは **red→green** の対で並べるのが既定: 先にテストを書くステップ（期待する振る舞いをテストコードで示し、人間が実行して失敗を確認する）、次にそれを通す実装のステップ（実行して緑を確認する）。テストの良し悪し・seam・モック方針の基準は tdd skill に従う
- 対を免除できるのは次の閉じたリストのみ: 設定・マイグレーション・ドキュメント・コマンド生成ファイル・既存関数を呼ぶだけの結線。**副作用（DB・外部API・ファイルIO）はモック境界でテストできるので免除理由にならない**。「モックだらけで割に合わない」等の判断でテストを外したいときは、勝手に外さず「この手順書でやらないこと」に判断ごと書いて人間に委ねる
- ステップの「なぜ」やコードコメントで主張した不変条件（呼び出し順序・失敗時に何を書かないか・例外を外に出さない等）は、散文で終わらせず、それが破れたら red になるアサーションを対のテストに含める。人間は手順書のコードを最小diffに縮めて写すことがあり、散文の意図はそこで落ちる — 落ちたら red になるテストだけが守る
- テストの説明文（RSpecの `it` / `describe`、Goの `t.Run` 名、`test` のタイトル等）は日本語で、期待する振る舞いをそのまま書く（例: `it "未ログインなら401を返す"`）
- ステップは実装順（この順に書けば途中状態でも壊れにくい順）に並べる。既存の不具合を先に直す必要がある場合は、それを最初のステップに置く
- コードは省略しない。写す単位で完全に載せる。既存ファイルの修正は、変更箇所の前後関係が分かる形（変更前→変更後、または該当ブロック全体）で載せる
- コード中には意図のコメントを添える。自明でない分岐・順序・回避策・境界値に付け、写経する人間が判断を追えるようにする
- コマンドで生成されるファイル（lockfile・マイグレーション・codegen成果物等）は写経の対象にしない。「対象」をコマンドにしたステップとして書き、実行後に何が生成されるはずかを添える
- 「なぜ」もコード中のコメントも、差分から読み取れない判断だけを書く。コードを読めば分かる説明や型の言い換えは書かない
